## Cómo se aplica (clics exactos)

1. Respaldo en Railway: Postgres → **Backups → Create backup**.
2. Con la app corriendo y tu PIN (`TRADE_PIN`), desde la carpeta del repo:
   ```
   python scripts/import_companies.py --lote1 --out lote1.json
   python scripts/import_companies.py --plan lote1.json --md plan.md            # sin categorías nuevas
   python scripts/import_companies.py --plan lote1.json --approve-cats --md plan.md   # aprobando las 56
   ```
   Lee `plan.md`. La huella que exige el servidor es LA DEL SERVIDOR (otro grafo, con vínculos pendientes), así que
   planea también allí y copia ESA `plan_sha`:
   ```
   python scripts/import_companies.py --plan lote1.json --server https://<tu-app>.railway.app --pin <PIN> --md plan_servidor.md
   ```
3. Aplicar por la API (sube el archivo en trozos y exige la MISMA huella; si el grafo cambió → 409 y vuelves a planear):
   ```
   python scripts/import_companies.py --apply lote1.json --server https://<tu-app>.railway.app --pin <PIN> \
       --plan-sha <plan_sha> --confirm-db railway
   ```
   `--confirm-db` es OBLIGATORIO (el nombre exacto de la base, como en reconcile; sin él → 400 `confirm_required`).
   Respuesta: `run_id`, `decision_id` (libro: `ontology.bulk_import`), eventos escritos, versión del grafo antes/después.
4. Ver corridas: `python scripts/import_companies.py --runs --server …`. Deshacer (de la más nueva a la más vieja, con
   decisión `ontology.import_rollback`): `--rollback <run_id> --confirm-db railway --server … --pin <PIN>`.

Sin servidor (terminal con `DATABASE_URL`): `--apply lote1.json --db --plan-sha … --confirm-db <nombre>` escribe
directo, también con UNA decisión (principal `system:import_cli`).

## Contrato de la API (para el panel 🩺 → 📥 Importar, pendiente)

- `POST /api/ontology/import/files` (PIN) `{name, sha256, chunk, chunks, data (base64 zlib), encoding}` → `{status: partial|stored,
  sha256, n_records, n_updates, batch}`. Trozos ≤ 900 KB comprimidos (`policy.import.upload_chunk_max_bytes`).
- `POST /api/ontology/import/plan` (PIN) `{file_sha | records[, updates], approve_categories?, batch?, full?, format?: json|md, lang?}`
  → `{plan: {counts, categories.to_approve, what_changes, plan_sha, items[{record_id,name,action,id,method,score,conflicts,
  warnings,links[]}], updates[], invalid[]}}`. No escribe.
- `POST /api/ontology/import/apply` (PIN) `{file_sha | records, approve_categories?, confirm_db (obligatorio), expect: {plan_sha}}` →
  `{status, run_id, decision_id, events, objects_created, objects_updated, links_created, links_dedup, pending, quarantine,
  graph_version_before, graph_version_after, elapsed_ms, gate_import, gate_links}`; 409 `plan_changed|graph_changed|busy`,
  422 puerta en bloqueo, 503 `ledger_unavailable`, 400 `confirm_required`. `graph_changed` también salta si la base avanzó
  desde el plan aunque la vista rápida no se haya reconstruido.
- `POST /api/ontology/import/rollback` (PIN) `{run_id, confirm_db (obligatorio)}` → `{run_id, links_retracted, objects_retired,
  objects_restored, events_written, decision_id}`; 409 `already_rolled_back|later_runs`.
- `GET /api/ontology/import/runs?limit=` → `{runs[], pending_links, policy}` (`graph_version_after` se deriva de
  `kh_tx_versions` por la transacción de la decisión; los pendientes ya resueltos no se vuelven a resolver).
